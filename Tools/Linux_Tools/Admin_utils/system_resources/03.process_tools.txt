1. Quick One-Liner for All Running Java Processes

for pid in $(pgrep -d ' ' java); do 
    echo "--- PID $pid ---"; 
    grep -E 'Name|VmRSS|VmSize|VmSwap' /proc/$pid/status; 
done

What the key /proc metrics mean:
• VmRSS: The actual physical RAM currently consumed by the Java process. This is the most accurate indicator of real memory footprint.
• VmSize: The virtual memory size. This is just reserved address space and does not reflect actual RAM usage.
• VmSwap: The amount of memory the process has swapped out to disk.


2. Neatly Formatted Table View

If you want a clean overview that aggregates all Java processes, calculates their memory from /proc in Megabytes (MB), and lists them in a clean table, use this script:
bash
echo -e "PID\tProcess\t\tActual RAM (RSS)"
echo -e "----------------------------------------"
for pid in $(pgrep java); do
    if [ -d "/proc/$pid" ]; then
        name=$(grep "Name:" /proc/$pid/status | awk '{print $2}')
        # Extract VmRSS in KB and convert to MB
        rss_kb=$(grep "VmRSS:" /proc/$pid/status | awk '{print $2}')
        if [ ! -z "$rss_kb" ]; then
            rss_mb=$(echo "scale=2; $rss_kb / 1024" | bc)
            echo -e "$pid\t$name\t\t${rss_mb} MB"
        fi
    fi
done


3. Digging Deeper (Why is Java using so much?)

Keep in mind that the operating system's RSS reading includes both the Java Heap and Native Memory (metaspace, thread stacks, GC overhead, and loaded libraries).
If you notice a specific Java process ID (PID) using a massive amount of RSS, you can see how that memory is distributed using Java's built-in diagnostic tool:
bash
jcmd <PID> VM.native_memory baseline

##The difference between VIRT, RES and SHR:

VIRT stands for the virtual size of a process, which is the sum of memory it is actually using, memory it has mapped into itself (for instance the video card's RAM for the X server), files on disk that have been mapped into it (most notably shared libraries), and memory shared with other processes. VIRT represents how much memory the program is able to access at the present moment.

RES stands for the resident size, which is an accurate representation of how much actual physical memory a process is consuming. (This also corresponds directly to the %MEM column)

SHR indicates how much of the VIRT size is actually sharable memory or libraries. In the case of libraries, it does not necessarily mean that the entire library is resident. For example, if a program only uses a few functions in a library, the whole library is mapped and will be counted in VIRT and SHR, but only the parts of the library file containing the functions being used will actually be loaded in and be counted under RES.
